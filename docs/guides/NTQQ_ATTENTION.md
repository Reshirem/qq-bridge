# 脱离 SnowLuma 的 QQ 来信与角色提醒

2026-11-10 在已登录的 Windows QQ `9.9.36-53644` 上做了两组只读实验。一个 SQLCipher 连接可以同时服务新消息检测和按来源查历史。QQ 自身也能直接提供带正文的来信事件。本页前半部分记录当前运行方式，后半部分保留选型实测。

## 当前运行方式

在 WebUI 的「QQ 消息 → 提醒与发送」中选择「QQ 接入方案」，点击「应用并重启桥接」。配置字段为 `qqBackend`，取值 `native` 或 `snowluma`。旧配置缺省使用独立通道。通过 `start.bat` 启动的守护窗口会拉起新进程，直接运行 Node 的部署需自行再次启动。总览和系统运维显示实际运行的后端。

切回独立模式后，桥接恢复本账号尚未确认的提醒。断线补查以本次启用独立模式的时间为下限。独立模式在已登录但空闲的桌面 QQ 上会主动发起一次只读服务查询，接通后来信和工具共用这个通道。

「提醒规则」提供总开关，以及私聊、原生 @、回复/引用、人格卡名称、关键词、戳一戳六个开关，默认开启，保存后立即生效。关闭某类提醒会清掉该类的待发和未读补提醒；不限制主动读消息、发送、图片缓存或后台学习。戳一戳按 QQ 的功能事件和目标账号识别，自定义动作文字与后缀不影响识别。只提醒别人对当前账号使用该功能的事件；群聊和私聊共用此项开关。原生通道会在历史和断线补查中按原消息 ID 向 QQ 解析灰条事件，不把灰条显示文字当成识别依据。

- **独立通道**用本机命名管道连接已登录 QQ 的消息服务。新消息由 QQ 回调触发。历史、引用与已知消息 ID 优先使用同一个账号专属只读数据库连接，媒体在 QQ 的本地目录按需查找。数据库暂不可用时，历史查询也可使用当前 QQ 消息服务。状态页分别显示 QQ 连接和数据库连接。
- **独立模式的未读数**是待阅读提醒的位置数。普通聊天走历史工具，没有每个群 500 条的上限。角色读取后确认提醒，WebUI 预览保留提醒。每个账号独立保存提醒的来源、原生消息 ID、序号、触发原因、投递与确认状态。已读提醒的短期标记用于断线补查去重。聊天正文、图片和好友历史不会复制到 SnowLuma 的缓存库。开启后台学习时，待分析任务只记录 QQ 消息位置，执行时读取正文与图片。已确认的学习成果和记忆按各自模块管理。
- **SnowLuma 通道**继续使用其 WS、HTTP、心跳和原有本地未读库。选用独立通道时，桥接不会连接或探测 OneBot。选用 SnowLuma 时，桥接不会附加 QQ 进程、打开独立提醒库或启动原库读取进程。两种模式使用同一 DSH 角色会话和 `mcp__qq__*` 工具。角色可通过 `mcp__qq__qq_status` 查询当前后端。

「未读补提醒」另有独立开关（`socialV2.reminders.unreadFollowup`），默认开启：已提醒但未读的消息在后续休息期间每分钟检查一次，最多补发一次。关闭后取消补提醒定时器与待发补提醒，不影响新事件的首次提醒。

### 新机器安装

在运行桥接的 Windows x64 电脑上，用同一 Windows 用户登录一个桌面 QQ 主进程，安装 64 位 Python 3.12。从 **qq-bridge 仓库根目录**打开 PowerShell。桥接启动时按下面两个固定路径查找 Python。 下例用 `py -3.12` 选择解释器。若未安装 `py` 启动器，可将两处 `py -3.12` 换成指向 64 位 Python 3.12 的 `python`，或 PowerShell 写法 `& 'C:\实际安装目录\python.exe'`。

先准备实时收发所用的 Frida 环境。项目已在 QQ `9.9.36-53644` 验证这一组合。

```powershell
py -3.12 -m venv state\ntqq-probe\venv
.\state\ntqq-probe\venv\Scripts\python.exe -m pip install --only-binary=:all: frida==17.24.1
```

再准备历史和媒体读取器。最后一条命令下载并校验 SQLite 头文件，在 `state\ntqq-reader\` 生成 `ntqq_vfs.dll`。

```powershell
py -3.12 -m venv state\ntqq-reader\venv
$reader = '.\state\ntqq-reader\venv\Scripts\python.exe'
& $reader -m pip install --only-binary=:all: -r scripts\ntqq-requirements.txt
& $reader -m pip install --only-binary=:all: ziglang==0.13.0
& $reader -B scripts\build_ntqq_vfs.py
```

首次使用需准备**当前 QQ 账号的数据库密钥**。已有密钥可以直接导入。需要首次取钥时，可参考 QQDecrypt 的 Windows 教程并核对其验证版本。本项目的读取器接受已取得的密钥，导入时会实际开库核验。[Windows NTQQ 取钥说明](https://github.com/QQBackup/QQDecrypt/blob/0dba968ebcb9ba23a68571780eb6b53687f77493/docs/decrypt/extract/NTQQ%20%28Windows%29.md)

```powershell
& $reader -B scripts\ntqq_history.py --import-key
& $reader -B scripts\ntqq_history.py
```

第一条命令在终端内隐藏输入，成功返回 `keyStatus: imported`。第二条只报告读取模式、密钥状态和记录条数，预期为 `live-readonly`、`cached`。以后在同一台机器、同一 Windows 用户下，读取器按 QQ 账号和数据库头标识复用 `state\ntqq-reader\keys\` 中的 DPAPI 密钥。已有有效缓存的安装可以直接执行第二条。

### 启动后核对

1. 运行桥接，打开 WebUI「系统运维 → 诊断与维护」，在「QQ 消息通道」确认出现「独立通道已连接」和「原库只读连接已就绪」。前者表示 QQ 收发服务已连接，后者表示数据库查询可用。
2. 若 QQ 已连接但原库未就绪，检查上面第二条命令能否读库，以及 QQ 是否打开 `%USERPROFILE%\Documents\Tencent Files\<QQ号>\nt_qq\nt_db\nt_msg.db` 和对应 WAL。常驻读取器目前固定使用这个数据目录。诊断命令的 `--tencent-files` 只对当次命令生效。QQ 保持连接时，读取器失败后约 30 秒再试。
3. 在「QQ 消息 → 消息来源」查看待阅读提醒。独立模式下普通群消息可从历史读取，未读提醒为零也可以有新聊天。原角色调用 `mcp__qq__qq_status` 可核对后端为 `native`。[DSH 工具验收](DSH_SETUP.md#验证)

独立模式已对照真实的群聊、私聊历史、按 ID 定位、来信、群成员与收藏图片。发送使用当前 QQ 的提交结果和状态回执，超时不会自动重发。群聊、私聊的主动「戳一戳」已接入消息服务 `sendNudge`，角色继续使用 `qq_send_poke`；关闭接收戳一戳提醒不影响主动发送。已核对本机方法及绑定，并完成离线参数、回执和拒绝路径测试；尚未向真实联系人实发验收，详见 [发送验证边界](NTQQ_SEND.md)。合并转发详情尚未接入 QQ 原生接口，会明确返回未支持。

## 一个常驻只读连接

由桥接启动一个本机读取进程，每个登录账号使用一个连接。桥接检测来信和角色的历史工具都向这个进程请求数据。每个数据库请求使用一个短读事务，媒体文件在事务外查找。空闲时保留连接。这样下一次查询就能看到新提交，长期占用旧快照则会影响 WAL 检查点推进。常驻读取器会先结束 `open_live` 用于验证数据库的初始事务。[现有读取器](../../scripts/ntqq_history.py) · [SQLite WAL 并发](https://sqlite.org/wal.html#concurrency)

本机库 80 MiB，约 8 万条群消息、1,767 条私聊。选同一大群和同一私聊，预热后在同一进程测查询与正文解码，单位为毫秒、中位数。前两列各测 7 次，索引实验测 8 次。计时不含进程启动、媒体查找和模型调用。

| 最近消息 | 每次重新开库 | 同一连接，现有 SQL | 同一连接，使用 QQ 已有索引 |
| --- | ---: | ---: | ---: |
| 群聊 20 条 | 326.7 | 314.1 | 0.16 |
| 群聊 100 条 | 394.2 | 397.0 | 0.64 |
| 私聊 20 条 | 13.1 | 1.46 | 0.13 |
| 私聊 100 条 | 13.0 | 2.74 | 0.68 |

现有群查询按群号筛选、按时间和主键排序，执行计划是整表扫描加临时排序。实验查询用 `40027` 缩小到索引范围，同时用 `40030` 核对目标，群聊按群内序号取最近消息。两种页长在这两个来源上逐条 ID 和顺序相同。全库存在多个来源共享一个 `40027`、单个来源对应多个 `40027` 的情况。上线前需覆盖多来源、旧记录、同秒分页和乱序，保留历史工具原有的翻页顺序。

空闲时每 250 毫秒在同一连接上取一次 `PRAGMA data_version`。32 秒共 128 次，中位 0.051 毫秒，最大 1.903 毫秒。观察到两次版本变化，其中一次查到消息表最大主键变化。版本号只提示有其他连接提交过数据，具体涉及哪些消息仍需查询。这组耗时只覆盖变化检查。[SQLite 对 data_version 的定义](https://sqlite.org/pragma.html#pragma_data_version)

单独比较了消息时间与原生 ID。79,673 条带时间的群记录中，78,049 条的 ID 小于更早秒内就已经出现过的最大 ID。私聊为 568 / 1,776。消息时间与写入时间可能不同，这项统计不能换算成漏收比例，但足以排除用最大消息 ID 表示历史新旧的做法。

## QQ 原生接口和数据库能识别哪些提醒

| 数据来源 | 本机结果 | 用途 |
| --- | --- | --- |
| QQ 未读提醒摘要 | 在两个群分别调用 `getFirstUnreadAtmeMsg`、`getFirstUnreadAtallMsg`、`getFirstUnreadAtMsg`，均返回 `result=4`，没有取到可核实的未读 @。 | 可继续核对 QQ 客户端显示的未读 @。本次没有验证阳性样本，角色名、自定义关键词仍需要消息正文。 |
| QQ 的 `onRecvMsg` | 15 秒内收到两条真实群消息，均有原生 ID、序号和发送者。QQ 消息的文字元素有 `textElement.content`。 | 桥接直接检查本条消息中的文字和结构化元素。匹配角色名或关键词只需本地字符串比较。QQ 重登后要重挂监听，客户端升级后须复验。 |
| 直读原库 | 将 186 条群聊和 24 条私聊历史与 QQ 消息服务按原生 ID、来源对照。数据库正文中可读出文字、@ 类型、目标 UID 和被引用者 UID。 | 已落库的私聊、群 @ 自己、回复自己及关键词都可以在同一读取进程识别。常驻读取器已按结构化字段解析。 |

历史样本优先选含 @ 或引用的记录，用来校验字段，不代表群内各种消息的占比。[QQ 消息服务接口参考](https://github.com/NapNeko/NapCatQQ/blob/98d781d19815d1625b24d717ce280ecf0a4f6d0c/packages/napcat-core/services/NodeIKernelMsgService.ts) · [QQ 消息库正文参考](https://github.com/QQBackup/nt_msg_db_util/blob/master/db_docs/c2c_msg_table/40800.md)

另做一次 45 秒并行观察。同时打开 QQ 来信监听和数据库只读连接，收到两条来自他人的群聊，回调均带文字内容。保持 250 毫秒轮询，经原生 ID 在数据库首次查到两条消息，距各自 QQ 回调为 20 和 131 毫秒。此测量已知道要查的 ID，只验证这两条记录何时可见。纯数据库方案自行发现新消息的端到端时延、繁忙时段表现和私聊实时回调仍待测。

- **群 @**。78 个原生个人 @ 的类型和目标 NT UID 都分别与库内文字段的 `45102`、`45105` 一致，其中 20 个指向本账号。只有 72 个同时提供有效的数字 QQ 号。216 个普通文字段的 `45102` 均为 0，其中 12 个正文含手打的 `@`。可用结构化目标判断点名，再用本条正文独立匹配关键词。样本未覆盖真实的 @ 全体。
- **引用回复**。108 个引用元素均带原作者 `senderUidStr`，与库内引用段的 `40020` 逐个一致。QQ 接口在这批引用上均未给出有效数字 `senderUin`。107 个群引用按同群原消息序号在库内均查到唯一原文，作者全部匹配，其中 8 个引用本账号。另取 12 个引用调用 QQ 的 `getSourceOfReplyMsg`，作者也全部匹配。判断回复自己时先比对 NT UID，必要时回查同一来源的原文。关键词只匹配本条附言，跳过被引用的原文。

## 选型时的接入建议

1. **先让消息工具复用常驻读取器。** 桥接和 MCP 工具通过本机请求共享读取进程。一个历史请求只占用一次短查询。账号或数据库文件更换时重新绑定连接和账号各自的进度。本次用 QQ 进程打开的文件识别账号、用已验证的本机缓存密钥读取，全程无需向 SnowLuma 取钥。新账号首次获取密钥仍是独立依赖。[账号与密钥的现状](NTQQ_HISTORY.md)
2. **让数据库先旁路检测，和现有来信逐条核对。** 已知会话可使用群序号或私聊时间范围加重叠回查，并保留同一账号、会话、原生消息 ID 的去重记录。定期重新枚举会话，覆盖首次出现的好友和群。上线前单独测量繁忙时段的增量查询、迟到记录和断线补录。首次启动标记已有历史，重连时从上次确认写入的位置补查，保留未读工具现有的本地序号。原生 64 位 ID 全程用字符串。旁路阶段只计数，不投递提醒。
3. **让两个入口共用一次入账和提醒判断。** 数据库覆盖和时延达到要求时可以独立驱动提醒。如果同时启用原生 QQ 收发，优先用 `onRecvMsg` 投递实时来信，同一常驻连接负责历史和补漏。按账号、来源和原生 ID 去重后才写未读、交给后台学习和触发 DSH。同一条消息即使先走事件后落库也只处理一次。漏掉的记录只能补到 QQ 实际保留的范围。
4. **保留会话语义。** 继续使用桥接现有的运行中提醒、休息唤醒、失败重试和睡眠判断。睡眠时普通来信只缓冲，重连后不把睡眠期间的消息补发成唤醒，也不重执行历史中的主人命令。QQ 客户端的已读数与角色读取进度分别维护。切换数据源前按真实来信核对私聊、原生 @、引用自己、关键词、自发消息和重连重复入账。[现有触发策略](../../src/autonomy-policy.js) · [桥接与会话队列](../../src/bridge.js)
