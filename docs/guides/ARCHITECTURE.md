# 运行架构与渐进式重构

## QQ 接入方案

QQ 接入方案由启动配置 `qqBackend` 二选一。独立模式持有桌面 QQ 原生消息服务和账号对应的只读 SQLCipher 连接，独立提醒库只记录位置与投递水位。SnowLuma 模式使用 OneBot 事件和它自己的 500 条未读缓存。两者共用桥接的提醒分类、会话重试和出站审计。[运行方式](NTQQ_ATTENTION.md)

图片工具先从当前账号缓存读取可验证图片；普通图片及图片表情缺失时，按来源和原消息中的元素请求桌面 QQ 下载，并等待缓存验证通过后返回。商城表情读取本机预览或走已有 CDN 回退。历史正文查询本身不下载媒体。

## 当前方向

明日方舟能力由 `desktop-agent` 预设中的可选 Maa-Agent 插件提供。插件在存在本地安装记录时注册常用游戏工具和原生 CLI 入口，按需调用独立虚拟环境的 Python 模块。作业目录用于发现文件，执行工具也接受本地文件路径。作业执行、设备锁和战果记录由上游维护，角色使用同一运行编号查询进度。安装与使用见[明日方舟模块](MAA_AGENT.md)。

项目托管一个持久的全局 desktop-agent DSH 会话，作为可交流、可按需行动的数字角色。这里的“长期”指会话历史和角色设定可以接续；桥接在直接对话、QQ 提醒、WebUI 任务和生命周期恢复等事件后发起模型回合。模型休息时没有周期性心跳或持续观察。WebUI 是主要控制入口；电脑、QQ 和记忆是可按需使用的活动空间、渠道与能力。

## 身份与项目用词

- “数字角色”是产品定位用语，不是程序中的身份枚举。代码只维护一个 desktop-agent 会话，并按提示词规则处理交流与工具调用。
- 人格卡是用户维护的 Markdown 自由文本，程序不会解析物种或关系字段。当前选择保存在 state/current-role.json，并通过 qq-agent-presets 在每次 DSH system prompt 组装时动态注入；普通历史压缩不会移除这段固定前缀。卡片定义具体身份、形态、性格、兴趣、关系、行为习惯和表达方式。自然的聊天风格属于表达方式，不会自动把卡片设定的身体、感知或经历改成人类设定。
- 没有选中人格卡时，通用数字角色定位保留物种、外形、身体感知和关系称谓的开放性。宠物、朋友、搭档、主人或其他关系由卡片或实际互动确定，不设固定默认关系。
- ownerQQ 只锚定配置的 QQ 账号；每条已处理消息都保留结构化 `userId`，QQ 提醒也带发送者 QQ 号；`isOwner` 是桥接依据账号 ID 匹配出的消息字段，不定义角色之间的关系称谓。提示身份时以 `userId` / `senderId`、`isOwner` 与配置的 `ownerQQ` 为准，不以昵称或群名片作账号识别。`qq_get_owner_identity` 可读取当前设置或未配置状态供模型比对。当前人格卡、双方明确表达和来源内持续互动可决定该场合的关系表现；明确形成的角色扮演关系可以在该来源内延续，但不代表现实账号身份、跨来源关系或权限。来源内的日常状态或行程描述（如“回到家了”）只说明该发言者在该来源中的自述，不能单独证明其是主人/owner，也不能把其与其他来源中的账号对应起来。
- DSH 会话 ID、桌面会话状态和人格卡不会合并成一个身份字段：desktop-agent 是 preset ID，desktopAgent 是桥接内部名称，state/desktop-agent.json 与 state/current-role.json 是既有持久文件；/api/console/desktop-agent 是管理路由。历史 API 字段 globalCompanionSource 继续作为兼容字段，WebUI 展示为数字角色来源。以上名称保留以兼容 DSH、现有状态和客户端。
- 文档、preset 展示名和 WebUI 使用“数字角色”或“全局数字角色会话”；描述运行机制时写“活动回合”“休息”“恢复”，描述工具时写“电脑操作”“QQ 消息渠道”等实际能力。

继续按明确职责渐进式整理 `src/bridge.js`，不需要为了代码体量整体重写。每次改动先找出状态所有者、持久化格式、调用方和安全门，再以小步迁移保持行为可审查。

## 当前运行行为

- `token-ledger.js` 将主会话、记忆整理和后台学习的用量存入 SQLite。`model-catalog.js` 缓存 models.dev 目录，按服务商和模型提供美元单价，账本保存每次采用的费率与金额。旧 JSONL 账本在一次事务内迁移。详见[令牌与花费](TOKEN_USAGE_CONSOLE.md)。

- `chat-learning.js` 独立持有后台学习队列、证据与知识库，`learning-runner.js` 负责批次专用 DSH headless 进程，`learning-api.js` 提供控制台管理，`learning-assets.js` 保存按内容哈希寻址的本地表情。新消息可自动进入该学习进程；主角色仍仅按需读取 QQ 正文。学习不创建逐 QQ 的聊天会话、不改变角色说话风格，也不调用 QQ 发送或 A_Memorix 工具。运行与持久化约定见 [CHAT_LEARNING.md](CHAT_LEARNING.md)。

- `sticker-memory.js` 由桥接把表情目录投影到独立的 A_Memorix 空间。QQ 工具按当前会话和普通表情、商城表情各自的使用开关，把检索命中映射回可发送的稳定 ID。关闭使用保留索引与本地素材。角色复检建议保存在学习库，WebUI 采纳后生效。
- `market-packs.js` 按包 ID 读取腾讯商城目录，WebUI 支持按包查找、预览、收录、编辑注解与移除。手动收录的商城表情和聊天学习条目共用本地素材存储、检索和发送机制，各有独立的管理视图。
- 收录时将整包视觉分析任务与条目一起提交到学习库。每包在一个独立的 DSH 会话中解释。商城原释义、当前注解和使用场景一起进入该张表情的索引。

- SnowLuma 提供 OneBot 事件流。桥接按 QQ 来源缓存收到的消息；普通群消息正文不会自动进入主角色的模型上下文。
- 群聊和私聊仍共用一个 DSH 上下文。固定前缀引导数字角色区分聊天场合：当前场合的普通交流可以自然参与；其他群/私聊的对话、人物、观点、关系、群内梗和未公开经历不主动带入，也不应因当前场合中的第三方请求而复述、概括或确认。私聊同样遵守来源边界；QQ 好友或好友列表只表示平台联系人关系，不自动表示信任等级、主人身份或信息分享授权。同一当事人主动提起自己此前私聊说过的事时，需能确认当前发言者与原私聊对象一致，再结合当前问题所需内容自然回应；边缘情况由模型按来源、内容和语境判断，示例不规定固定回复。这是模型行为约定，不是程序级跨群隔离或出站过滤。
- QQ 仅接受已配置 `ownerQQ` 的纯文本私聊 `/睡觉` 和 `/起床` 控制睡眠；其他聊天不作为管理命令执行。人格卡和桥接配置通过受保护的 WebUI 管理。关系称谓由人格卡和双方表达决定，单条生活描述、昵称、语气或玩笑不能单独建立主人/owner身份或跨来源账号关联。
- `ownerQQ` 首次由 WebUI 保存或清除后，本地值优先于 DSH 同名设置；此前的旧安装继续兼容 DSH 设置。账号改变时，缓存消息的身份标记按当前账号计算；QQ 工具访问范围不受该设置影响。
- 私聊、真正发给机器人的原生 @、已验证的回复/引用、群消息中提到当前选中的人格卡名称，以及配置的 `socialV2.attentionKeywords` 命中会向同一全局会话发送元数据提醒。会话活动时通过 DSH 的 `steer` 送到当前回合的下一步，休息时提前唤醒；提醒不含正文，数字角色可自行决定如何参与。
- 全局数字角色使用 `mcp-qq.js` 的 QQ 工具集，可访问账号中的群聊和私聊，不按提醒来源限制会话。项目工具守卫和桥接 API 仍校验当前 `desktop-agent` 会话与内部凭证；管理接口仅控制台可用，发送继续执行内容检查和审计。聊天隐私提示仍作为模型行为约定，而非会话访问隔离。直接通过 QQ 桌面 UI 发送不经过桥接 API 检查。
- 可选 A_Memorix 记忆的写入、相关度检索、单条读取和删除由 `a-memorix-gateway.js` 统一接入；DSH 工具、首次会话摘要和 WebUI 的常规记忆操作访问同一 namespace。DSH 记忆工具只校验全局 agent token，不受 `agent_rest` 生命周期限制。为支持全量原始记录浏览，已登录的本机 WebUI 还可通过独立适配器只读分页查询该 namespace 的 metadata SQLite `paragraphs` 表；该读取仅供控制台使用，agent-call 白名单不开放此路由。桥接不直接写入 SQLite，也不读取向量库或图文件；调用参数中的记忆正文和搜索词不会进入工具参数日志。设计和部署前提见 [MEMORY_ARCHITECTURE.md](MEMORY_ARCHITECTURE.md)。
- `dsh-computer-use-win` 提供本机桌面操作能力；数字角色可根据需要观察用户的电脑活动。插件支持部分后台操作和由用户通过 Esc 停止桌面操作；普通鼠标或键盘操作不会自动停止工具。ChatGPT、DSH、qq-bridge 和 SnowLuma 的 GUI 在无关任务期间保持受保护。详情见 [RULES.md](../../RULES.md)。
- DSH 原生 `web_search` / `web_fetch` 由 `@deepseek-ai/dsh-tool-web` 注册，分别调用当前 DSH profile 选择的 `ctx.web` 搜索/抓取提供方；desktop-agent preset 沿用 `tool-web` 的默认配置，默认注册两项。`qq-tool-restrict` 允许这两个 DSH 工具名通过执行守卫，实际是否可调用由 DSH 工具注册和每步提供方就绪状态决定。它与桥接的 `webSearch` / `web-search-safe` 不同；随附的 DSH `http` 抓取提供方允许访问本机和内网地址，不经过桥接 SSRF 防护。
- 全局会话生命周期为 `idle`、`active`、`resting`、`recovering`、`sleeping` 和 `stopped`。活动回合最后调用 `agent_rest`；休息为 1 至 5 分钟，到期后恢复一轮；用户在 DSH 对话中发消息、提交 WebUI 任务或收到有效 QQ 提醒，都可提前结束普通休息。`sleeping` 由 ownerQQ 私聊命令进入并持久保存，清除提醒，禁止自动唤醒，消息仍缓冲；`/起床` 恢复一轮。DSH 直接启动的回合会被桥接请求取消。
- 如果活动回合刚通过 QQ 回复某个来源，数字角色会在休息前用最近一次 `readThroughSeq` 检查该来源是否有新未读；桥接会清掉角色已读消息对应的排队提醒，避免同一消息重复唤醒。
- 桥接运行期间，角色读到触发提醒的消息时，桥接会确认该条提醒。若它仍未读，会话进入休息后由单一全局计时器每分钟检查一次，最多补发一次。
- 异常回合退避时，新到的 QQ 提醒留在桥接队列，暂停未读补提醒。如果 DSH 已经开始新回合，桥接把等待的提醒提交给该回合的下一步。如果到重试时间会话仍空闲，恢复提示会带上排队的 QQ 提醒。桥接重启后重新订阅原主会话。会话事件流重连时，桥接从快照确认休息前的回合是否已经结束，随后继续处理排队的提醒。
- 消息提醒与 QQ 工具使用 `id:` 和 `seq:` 区分 QQ 消息 ID 与本地序号；有歧义的纯数字会返回明确提示。缺少 QQ 消息 ID 时提醒中的本地序号会带缓存标识；清空 QQ 缓存时同步丢弃待处理提醒，并使之前的本地序号提醒失效，避免序号重新指向新消息。
- 回合没有调用 `agent_rest` 就结束时，桥接按 1、2、4、8、16 分钟尝试恢复，之后间隔最长 30 分钟。WebUI 停止会取消当前和排队中的 DSH 工作并持久进入 `stopped`；只有 WebUI 手动启动或提交任务才解除停止态。
- QQ 等待工具及其静默判断已移除。模型自行决定下一步，新的 QQ 事件沿用提醒规则。
- `state/desktop-agent.json` 保存桥接管理的全局会话 ID、令牌和生命周期。DSH 负责保留会话历史；桥接仅管理当前配置指向的全局会话。
- Windows 上已有独立的 [NTQQ 历史只读实验](NTQQ_HISTORY.md)，用 SQLCipher 和 Windows 只读 VFS 直接查询登录账号的原库与 WAL，通过 Windows DPAPI 复用已核验的账号密钥。运行中的桥接仍通过 SnowLuma 接收事件、查询历史和发送消息。

当前权限约定见 [RULES.md](../../RULES.md)，安装过程见 [DSH_SETUP.md](DSH_SETUP.md)。长期记忆目标与实施边界见 [MEMORY_ARCHITECTURE.md](MEMORY_ARCHITECTURE.md)。

WebUI 的 QQ 消息仪表盘展示来源缓存、未读与待处理提醒。关闭提醒会清除待发提醒；旧版持久暂停在升级时迁入此开关。睡眠期间只缓存来信。角色使用表情工具、同步 QQ 收藏、后台学习表情各有独立开关。通道设置按页面分组保存，保存后仅保留当前支持的配置项。

## 当前代码边界

`src/bridge.js` 仍是组合与协调中心，涵盖启动配置、OneBot 事件、全局 DSH 生命周期、QQ 消息缓存、WebUI HTTP 路由和发送策略。共享状态较多，所以优先从可独立定义输入输出的职责开始拆分。

已有边界包括：

- `src/autonomy-policy.js`：纯函数形式的 QQ 注意信号分类。
- `src/dsh-client.js`：DSH API、鉴权和事件流客户端。
- `src/mcp-qq.js` 以 `mcp__qq__*` 注册 QQ 消息、媒体和状态工具，桥接按所选后端执行。
- 媒体、角色卡、网络抓取、敏感内容和 token 账本等独立模块。

## 渐进式重构顺序

把以下职责作为可逐步明确的边界，不强制采用固定目录结构：

1. **运行时组合**：启动、依赖接线与关闭流程。
2. **QQ 网关**：OneBot 事件归一化、消息缓存和 QQ 出站传输。
3. **全局会话管理**：唯一 `desktop-agent` 会话的创建、恢复、停止与状态持久化。
4. **自主调度**：休息、异常恢复、注意信号与活动回合协调。
5. **QQ 消息存储**：按来源索引、去重、水位和按需读取；与将来的数据库适配器保持小接口。
6. **控制台 API**：将管理路由与会话、消息和发送策略解耦。
7. **动作策略**：集中说明 SnowLuma 发送的授权、内容检查和审计边界，并保留用户允许的桌面控制能力。

## 改动原则

- 一次处理一个具体职责，先确认它读写的状态与所有调用方。
- 抽取时传入窄依赖，避免模块反向依赖桥接入口形成隐式全局耦合。
- 结构整理应保持既有行为；有意改变行为时，同步更新 RULES、文档、控制台和持久状态迁移。
- 不要把 QQ 消息正文或关键词信号自动塞进全局模型上下文。活动检测和模型观察是两件事。
- 不要在清理中重新引入逐群/逐私聊 DSH 会话、逐来源 agent 令牌或并行运行时。
- 发送授权检查应保持集中，覆盖桥接 API 发送；桌面 GUI 发送的限制另见当前用户授权与 [RULES.md](../../RULES.md)。
- NTQQ 历史的下一项接入工作是补查旧消息，先核对消息标识与两端覆盖差异。实时提醒继续使用 OneBot 事件。

## 何时考虑整体重构

只有当单一全局会话的具体功能无法通过小步整理实现，或共享状态让迁移风险不可接受时，才重新评估更大规模重构。先明确可验证的边界、迁移方案和失败回退，再决定是否更换整体结构。

## QQ 缓存与发送

桌面 QQ 的[进程内原型](NTQQ_SEND.md)可以独立于桥接运行。只读命令验证账号、收藏和原生来信，独立的发送测试命令可向经核对的私聊提交文字或纯表情并记录 QQ 状态回执。生产角色仍走已有的 OneBot 收发、去重和未读逻辑。

每个群和私聊最多保留 500 条未读。双方聊天历史由 SnowLuma 的 `get_group_msg_history` 和 `get_friend_msg_history` 提供，角色用 `qq_get_conversation_history` 按消息 ID 翻页。自己的近期消息和活跃成员也从远端历史筛选。角色读取未读页或单条详情时，桥接自动扣除返回的来信。历史页按同一来源的 QQ 消息 ID 逐条匹配。跳读保留间隙中的未读，补齐间隙后连续水位才会前进。每个来源在内存保留最近读过的 100 条来信供后续引用、查看媒体和定位无 QQ ID 的消息。超出后仍可按 QQ 消息 ID 从所属来源查询历史。

`qq-unread-store.js` 使用 SQLite WAL。每条来信只向对应来源插入新序号并删除已读或溢出记录，元数据与队列写入同一事务。重启后恢复剩余未读和序号，包括跳读后留下的间隙。清空操作在事务内替换缓存标识与队列。旧 `social-v2.json` 仅在数据库未初始化时导入，提交后移除旧文件，重启不会重新导入旧数据。格式损坏时停止启动并保留原件。

发送数量由模型决定，桥接无多条开关和数量上限。后续每条消息前等待 `min(1000, 下一条Unicode字符数 × delayPerCharMs)` 毫秒，第一条直接发送。默认 20 ms/字，设为 0 可连续发送。随机、长停顿和模型指定间隔参数已移除。
