# 直接读取 Windows QQ 历史

在 Windows 上，`scripts/ntqq_history.py` 可以查询当前登录账号的 `nt_msg.db`。默认只报告群聊和私聊的记录数。给定来源后，输出该来源的消息，最新在前，可继续向前翻页。QQ 保持登录，诊断脚本直接按 QQ 打开的数据库识别账号。此脚本独立于角色会话、未读水位和记忆整理。

## 使用

新机器先按独立通道说明安装读取器、构建 VFS 并导入数据库密钥。然后在 qq-bridge 根目录运行下面的只读诊断命令。[新机器安装](NTQQ_ATTENTION.md#新机器安装)

```powershell
$reader = '.\state\ntqq-reader\venv\Scripts\python.exe'
& $reader -B scripts\ntqq_history.py
& $reader -B scripts\ntqq_history.py --source group:123456 --limit 20
& $reader -B scripts\ntqq_history.py --source private:123456 --limit 20
```

将示例号码换成实际群号或好友 QQ 号。下一页沿用同一来源，另传 `--before-id` 和上一页最后一行的 `nativeId`。时间相同的记录按主键排序。此 ID 是原生库行标识，不能直接用于 SnowLuma 的发送、引用或未读确认。聊天正文只随有来源的查询输出。

默认在 `%USERPROFILE%\Documents\Tencent Files\当前账号\nt_qq\nt_db` 查找消息库。重定向了文档目录或自选了 QQ 数据目录时，命令行诊断可用 `--tencent-files` 指定 `Tencent Files` 的完整路径。常驻读取器使用默认路径。两种读取方式都需要 QQ 在线打开该库，并有可读取的 WAL 索引。

## 在线读取

QQDecrypt 的解密工具会导出剥除文件头的中间库和明文 SQLite 库，适合离线分析。它的 Linux 研究记录观察到同一账号多次登录时数据库密钥相同，已有库的 `key_meta` 通常也保持稳定。本读取器用该标识复用经过验证的密钥。查询历史时直接访问原库，取完一页消息便关闭读事务，再解析图片和视频缓存。[QQDecrypt 解密流程](https://github.com/QQBackup/QQDecrypt/blob/main/docs/decrypt/decrypt_db.md) · [密钥研究](https://github.com/QQBackup/QQDecrypt/blob/main/docs/research/NTQQ-Linux-DB-Key-Research.md)

1. 按 Windows 报告的 QQ 进程和文件句柄识别账号，再用账号与原库 `key_meta` 定位已验证的 DPAPI 密钥。若密钥尚未导入，可用 `--import-key` 输入密钥并验证。独立通道全程无需调用 SnowLuma。
2. 读取器加载 `state/ntqq-reader/ntqq_vfs.dll`，通过 SQLCipher 直接打开 QQ 原文件。该 SQLite 文件系统适配器只对主库读取偏移加 1024 字节，并相应调整可见长度。主库和 WAL 的文件句柄都只读；共享内存索引使用 Windows SQLite 的 `readonly_shm=1`。WAL 页位置和操作系统锁使用原生 Win32 VFS。每次查询持有一个读事务，能看到事务开始时已经提交的消息。源库不产生副本，源文件的写入、删除及创建均不属于该 VFS 的读路径。[SQLite WAL 并发读取](https://sqlite.org/wal.html)
3. 平时按需解密并核验访问的页。需要检查整库时传 `--check`，显式运行 `quick_check`。QQ 的 WAL 或共享内存索引不可用时，本次读取报错。VFS 一次编译即可复用；构建脚本下载并核验 SQLite 接口头文件，运行时使用 sqlcipher3 自带的 SQLCipher 引擎。[上游解密参数](https://github.com/QQBackup/nt_msg_db_util/blob/master/1.decrypt.py)
4. 群聊使用 `group_msg_table`，私聊使用 `c2c_msg_table`，两者都按 `40030` 匹配目标。通过 `40800` 正文内的有序 Protobuf 段提取文本和媒体引用。未识别或损坏的正文显式标记；当前输出不解析 @ 对象或引用目标。[上游消息结构](https://github.com/QQBackup/nt_msg_db_util/blob/master/db_docs/c2c_msg_table/40800.md)

## 合并转发

类型 16 的转发消息保留原生原消息 ID，并以 `native:<原消息ID>` 交给 `qq_get_forward_msg`。桥接调用 QQ 自身的 `getMultiMsg(peer, rootMsgId, parentMsgId)` 按需获取内容；它不依赖桥接预先保存转发正文。嵌套转发只接受本次连接中已经读到的节点，普通消息、错误来源和臆造的节点不能用来展开转发。转发内图片沿用缓存校验与按需补取，缓存未命中时根据 QQ 返回的真实节点和图片元素请求下载。读取失败不会保存成永久失败缓存，之后可以重试。

转发子节点不一定存在普通消息表中，因此图片使用 QQ 的 `downloadRichMedia`，以最外层来源和根消息 ID 加上已核验的内部图片元素 ID 定位；嵌套转发也沿用这一最外层定位。无需保留完整原生元素或额外下载凭据。桥接核对下载完成事件中的根消息和元素 ID；服务端拒绝时向工具返回数字错误码，不把未经核实的错误解释成图片过期。请求回执或成功通知都不能替代本地文件头和原图 MD5 校验。缺少缓存的商城表情仅在来源与表情身份验证后使用固定 QQ CDN 地址。每批图片最多两张并发，单张 45 秒、整批 135 秒预算，保留已完成图片；超时可单独重试。

图片工具默认 `quality=preview`：先查有效 Thumb，没有时用合限原图生成预览。角色需要高清细节时使用 `qq_get_image_detail` 的单张 `imageRef`，默认 `quality=original`，或提供归一化 `crop` 从原图裁剪；即使已有预览，缺原图时也会请求 QQ 补取。显式画质的源文件上限为 32 MiB，原图不会经过预览的 1280 长边缩图，而是保持尺寸重编码到最多 3 MiB 或明确要求裁剪。候选继续按来源、真实路径、文件头及原图 MD5 校验；已有缓存全部超限时明确报错，不重复下载同一大原图。省略画质的旧调用保持兼容。

返回尺寸和 `representation` 只描述桥接输出；DSH 附件层、provider 和模型服务仍可能再缩放或重编码。大图小字仍不清楚时，应继续从原图裁剪更小区域；这不会改变 QQ 原缓存，也不将局部读取描述成完整原图已核对。

## 图片、表情与视频

历史查询保留图文段的顺序，同时返回媒体标识和在当前账号 `nt_data` 中实际找到的文件路径。数据库里的 QQ 图片子类型 1 输出为 `sticker`，其他子类型保留在 `image.subType` 中。这表示发送时的图片类型，不能据此判断它是否仍在本账号的收藏里。系统表情输出 `faceId` 和可用的名称；商城表情输出 `packageId` 和 `emojiId`。

| `localFiles` 字段 | 含义 |
| --- | --- |
| `original` | 图片、图片表情或视频的本地原件。检查文件头，并核对整个文件的 MD5 与该消息记录一致。 |
| `thumbnail` | 图片或表情的可显示预览。商城表情通过表情包 ID 和表情 ID 定位本地 PNG。 |
| `cover` | 视频的封面图。 |
| 空对象 | 在当前支持的缓存目录中没有找到可验证的文件。独立诊断脚本仍只返回媒体标识，不下载附件。 |

原生 QQ 通道默认在收到新图片消息时后台检查并补齐 NTQQ 缓存；WebUI 可关闭此预取。无论预取是否开启，桥接的 `qq_get_message_images` 在普通图片或图片表情的缓存未命中时，仍会用已校验的来源、QQ 消息 ID 和该消息内匹配到的媒体元素 ID 请求 QQ 下载。下载请求提交后，桥接最多等待 12 秒，反复扫描缓存；原件仍须通过文件头与 MD5 校验，不把提交成功当作下载完成。商城表情先读 QQ 已保存的 `_aio.png` 预览，未命中时使用现有的受限 CDN 回退。查询只返回受限大小内的有效图片字节。无法定位原消息、下载失败或缓存校验不通过时，工具会保留明确的失败结果，不会读取任意路径。SnowLuma 后端仍沿用 OneBot 缓存和现有 CDN 回退。

2026-11-09 按同群、同消息、同发送者和时间对照 SnowLuma 的本机记录。在双方媒体段数量一致的消息中，8,402 个普通图片段、4,880 个图片表情段、372 个系统表情段、254 个商城表情段和 107 个视频段的分类逐段匹配。普通图片和图片表情的 MD5 均匹配，系统表情 ID 和商城表情的包 ID、表情 ID 也均匹配。103 个视频双方都有 MD5 且相同，另外 4 个视频的 SnowLuma 记录没有 MD5。另有 53 条群消息的媒体段数量不同，其中 52 条在 NTQQ 中只剩系统提示段。

文件层面抽查了普通原图、图片表情原图、两者的缩略图、商城表情预览和视频封面，每类 8 个文件均成功解码。另有 12 个图片表情原始 GIF 实测为 24 到 117 帧。本机原生库的 160 个视频段均找得到封面，这次在支持的目录内没有找到可核验的视频原件。另用生成的 MP4 验证了原件存在时的匹配与解码。

## 原库与 SnowLuma 记录对照及只读耗时

2026-11-09 至 2026-11-10 在 Windows 客户端和 SnowLuma 2.0.3 上实测对照：

- 一次通过完整性检查的原库包含 77,491 条群聊、1,752 条私聊。两个来源均取了 100 条，并从末条继续取 5 条，更早一页与上一页没有重复。
- 在一个群聊样本中，SnowLuma 返回的 11 条纯文本，其发送者、时间、正文全部与原生记录一致。在一个私聊样本中，15 条纯文本有 6 条一致；其余 9 条均为本账号发出，两边对历史本机自发私聊的覆盖范围不同（常驻读取器现也在群聊和私聊历史中保留本账号发出的记录及结构化灰条事件）。
- 2026-11-10 在 72 MiB 原库、同一大群和私聊上测量独立 CLI 进程（密钥缓存命中，每组预热一次再测五次，包含启动、账号识别、开库、历史查询和本地媒体解析）：

| 最近历史 | 旧版复制快照后读取 | 直接只读原库（CLI 单次进程） | 此前实测的桥接历史接口 |
| --- | ---: | ---: | ---: |
| 群聊 20 条 | 1,927 ms | 602 ms | 378 ms |
| 群聊 100 条 | 2,059 ms | 698 ms | 1,438 ms |
| 私聊 20 条 | 1,538 ms | 257 ms | 253 ms |

只读 VFS 直接读取去除了旧实验整库复制（约 72 MiB 临时文件）和默认全库 `quick_check` 的固定开销；桥接运行时进一步复用常驻只读连接（常驻连接内的查询耗时与提醒识别实测见 [常驻直读与角色提醒](NTQQ_ATTENTION.md#常驻只读连接与原生提醒识别实测2026-11-10)）。

- **原图本地读取耗时**：从同一群中选 4 张普通图片、4 张图片表情（大小约 52–1,654 KiB）。已取得消息标识且本地媒体目录索引就绪时，首次定位、校验并读出普通原图的中位数为 4.0 ms，图片表情为 1.3 ms；通过 SnowLuma 的 `get_image` 和 QQ 消息图片地址取得对应字节分别为 92 ms 和 109 ms，每张取三次（共 24 次）返回字节的 MD5 均与本地原图一致。
